1. Design Philosophy

Architecture Overview

Plagues has exactly three kinds of process and one broker. Once you have this picture, everything else in the wiki is a detail hanging off it.

The single most important arrow is the one that isn't there: an app never connects to a worker. That dotted "never" is the whole security model.

The three roles

Workers — privileged capability holders

A worker is a tiny MagicOnion-hosted service that exposes one or more capabilities. A capability is just a static C# method marked with Eclipse's [SeaOfDirac] attribute:

[SeaOfDirac("GetAccInfo", new[] { "accountName" }, typeof(PublicAccount), typeof(string))]
public static PublicAccount GetAccInfo(string accountName) { /* privileged work */ }

At startup a worker:

  1. Runs Notary anti-tamper over its own folder (or trusts the Manager's pre-launch check when Manager-managed).
  2. Reads the per-worker PSK and the Manager's public identity key, both handed to it out-of-band at launch (never on disk).
  3. Binds an ephemeral loopback port and publishes a WorkerAnnouncement (address + capabilities + public Kyber key + pid) so the Manager can find it.
  4. Serves the Eclipse protocol — but only completes a handshake for a peer that holds the PSK and presents a valid Manager signature.

See 2 - Creating a Worker.

The Manager — the trusted core

One Manager per machine. It is the only process that:

  • Checksums + launches + supervises every worker, restarting one that dies or trips its tamper guard.
  • Holds the master key (encrypts the permission store), the per-app PSKs, the per-worker PSKs, and its own Dilithium identity keypair.
  • Runs the broker: an Eclipse endpoint apps connect to. On each call it authenticates the app, checks XRUIOS.Permission, relays to the owning worker over a warm pooled session, and re-encrypts the reply.

See 4 - Registering and Launching.

Apps — untrusted consumers

An app holds only its own credential and the broker address. It never sees a worker, never holds the master key. It opens one Eclipse session to the Manager and calls capabilities by name:

await using var xruios = await EclipseSecureClient.ConnectAsync(brokerAddr, appId, appPsk, identity: appId);
var acc = await xruios.InvokeAsync<PublicAccount>("GetAccInfo",
    new() { ["accountName"] = Environment.UserName });

See 3 - Creating an App.

The trust rule that ties it together

Identity is bound by the tier above — never self-reported.
  • An app's identity is the appId the Manager minted for it. The app can't claim to be another app; the Manager resolves the PSK and checks permissions by that id.
  • A worker's peer is the Manager, proven by the Manager's signature (asymmetric), not merely by holding a shared secret.

This is the same discipline HangarBay uses for mods — bind the id, don't trust the claim — applied one tier up.

Two directions of encryption, both real

Eclipse's AeadChannel derives separate keys per direction (k_c2s, k_s2c) and gives each an independent AES-256-GCM cipher with a monotonic sequence counter. So a request and its reply are individually encrypted and authenticated, and neither can be replayed or reordered. The broker exploits this: it decrypts the worker's reply on the Manager→worker channel and re-encrypts the exact bytes onto the Manager→app channel, so end-to-end confidentiality holds across both hops without the Manager ever exposing plaintext to a third channel.
